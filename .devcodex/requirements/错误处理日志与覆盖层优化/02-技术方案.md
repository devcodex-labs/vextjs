## 二、类型扩展（`src/types/app.ts`）

在 `VextResponseConfig` 中新增 `logErrors` 字段，并新增 `VextLogErrorsConfig` 接口。

### 新增接口

```typescript
/**
 * 错误日志配置
 *
 * 控制 error-handler 在捕获到各类错误时是否向 logger 输出日志。
 * 未传时全部使用默认值。
 */
export interface VextLogErrorsConfig {
  /**
   * 是否记录未知 500 错误（含完整 err 对象和 stack trace）
   * 默认 true — 未知错误属于意外异常，必须可见
   */
  unknownErrors?: boolean;

  /**
   * 是否记录 HttpError 5xx（输出 error 级别日志，含 status 和 message）
   * 默认 true — 5xx 是服务端责任，需要在控制台可见
   */
  http5xx?: boolean;

  /**
   * 是否记录 HttpError 4xx（输出 warn 级别日志，含 status 和 message）
   * 默认 false — 4xx 属于客户端错误，高流量场景避免日志噪音
   */
  http4xx?: boolean;
}
```

### VextResponseConfig 扩展

```typescript
export interface VextResponseConfig {
  hideInternalErrors?: boolean;
  wrap?: boolean;
  /** 错误日志配置（可选，未传时使用各字段默认值） */
  logErrors?: VextLogErrorsConfig;
}
```

> **架构决策**：`logErrors` 与错误响应行为强绑定（同一个错误，同时决定"响应给客户端什么"和"记录什么到日志"），统一在 `response.*` 命名空间下便于用户集中配置。若未来错误处理配置大幅扩展，可拆为独立 `VextErrorConfig`；当前阶段字段数量（3 个布尔）不足以构成独立接口的复杂度门槛。

## 三、error-handler 改动（`src/lib/middlewares/error-handler.ts`）

### 3.1 函数签名变更

第 3 个参数 `logger` 完全可选，不传时行为与现在完全一致（向后兼容）：

```typescript
// 现在：
export function createErrorHandler(
  responseConfig: VextResponseConfig,
  devOverlay?: DevOverlayFn,
): VextErrorMiddleware

// 改为：
export function createErrorHandler(
  responseConfig: VextResponseConfig,
  devOverlay?: DevOverlayFn,
  logger?: VextLogger,        // ← 新增，可选
): VextErrorMiddleware
```

### 3.2 日志规则

| 错误类型 | 触发条件 | 日志级别 | 日志内容 | 默认 |
|---------|---------|---------|---------|:----:|
| 未知错误（500） | `logErrors.unknownErrors !== false` | `error` | `{ err }` 含完整 stack | ✅ |
| HttpError 5xx | `logErrors.http5xx !== false` | `error` | `[http-error] ${status} ${message}` | ✅ |
| HttpError 4xx | `logErrors.http4xx === true` | `warn` | `[http-error] ${status} ${message}` | ❌ |
| VextValidationError | — | 不记录 | — | — |

**为什么 HttpError 不记录 stack？**
HttpError 是业务代码通过 `app.throw()` 主动创建的预期错误，stack trace 指向 `default-throw.ts`
内部，对定位问题无意义。status + message 已足够描述错误。

### 3.3 执行流程

> ⚠️ **关键设计：日志记录必须前置于 devOverlay 判断**
>
> 现有 error-handler.ts 中 devOverlay 触发后立即 `return`（第 107 行），
> 若日志逻辑放在 devOverlay 之后，browser 访问场景下控制台将永远看不到日志。
> 正确做法：先记日志，再决定响应格式（JSON 或 HTML），两者正交互不影响。

```
进入 error-handler
      │
      ├── 【Step 1 — 日志记录（logger 存在时，先于响应格式决策）】
      │     ├── VextValidationError → 不记录
      │     ├── HttpError
      │     │     ├── status >= 500 && logErrors.http5xx !== false
      │     │     │     → logger.error(`[http-error] ${status} ${message}`)
      │     │     └── status < 500 && logErrors.http4xx === true
      │     │           → logger.warn(`[http-error] ${status} ${message}`)
      │     └── 未知错误 && logErrors.unknownErrors !== false
      │           → logger.error({ err }, `[uncaught] ${message}`)
      │
      ├── 【Step 2 — 响应格式决策】
      │
      ├── devOverlay && Accept 含 text/html
      │     → HTML 覆盖层（已有逻辑，不变）→ return
      │
      ├── VextValidationError
      │     → rawJson 422
      │
      ├── HttpError
      │     → rawJson(err.status)
      │
      └── 未知错误（500）
            → rawJson 500
              （hideInternalErrors 控制响应体是否含 stack，逻辑不变）
```

### 3.4 Import 变更

`error-handler.ts` 第 2 行已有 `import type { VextResponseConfig } from "../../types/app.js"`，在该行**追加** `VextLogger`：

```typescript
// 现在：
import type { VextResponseConfig } from "../../types/app.js";

// 改为：
import type { VextResponseConfig, VextLogger } from "../../types/app.js";
```

### 5.1 测试分组

## 六、架构质量评估（C15）

| 维度 | 评估 | 结论 |
|------|------|------|
| **可扩展性** | `logErrors` 配置化设计，未来可继续扩展日志目标（如输出到外部告警系统）而无需改 error-handler | ✅ 达标 |
| **可维护性** | logger 作为可选参数注入，error-handler 单一职责（响应格式化）不变，日志作为副作用在同一处集中处理 | ✅ 达标 |
| **易上手性** | 默认配置开箱即用（500/5xx 自动记录），不修改现有代码也能享受改善；需要定制时只加 `response.logErrors` 配置 | ✅ 达标 |
