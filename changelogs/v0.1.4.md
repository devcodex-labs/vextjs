# v0.1.4 Changelog

**Release Date**: 2026-03-06
**Type**: Patch (Bug Fixes + Dependency Pinning)
**Tests**: 1,984 passed (35 test files), zero regressions

---

## Summary

This release fixes four critical bugs that prevented `vext build && vext start` from working correctly. The root cause was a combination of CLI entry resolution errors, CJS bundle re-entry triggering duplicate bootstrap initialization, overly broad error handling in `detectAndStart()`, and missing `dist/package.json` in `BuildCompiler` output.

Additionally, three key dependencies (`schema-dsl`, `monsqlize`, `flex-rate-limit`) are now pinned to exact versions to prevent unexpected breaking changes from semver-compatible updates.

## Bug Fixes

### BUG-007 (P0): CLI Entry Resolution Error

**File**: `src/cli/utils/detect-project.ts`

**Problem**: `resolveEntryFile()` returned `<projectRoot>/dist/lib/bootstrap.js` when the user project had a `dist/` directory. However, the user's `dist/` only contains compiled user business code (routes, services, plugins, etc.) — the framework's `bootstrap.js` always lives at `node_modules/vextjs/dist/lib/bootstrap.js`.

**Symptom**: `vext start` after `vext build` failed with:
```
Error: Cannot find module 'E:\path\to\project\dist\lib\bootstrap.js'
```

**Fix**: `resolveEntryFile()` now always returns `project.entryFile` (the framework-internal bootstrap path), regardless of whether `dist/` exists. The presence of `dist/` is communicated to bootstrap via the `VEXT_BUILT=1` environment variable, which bootstrap uses to decide whether to load user code from `dist/` or `src/`.

**Before**:
```typescript
export function resolveEntryFile(project: ProjectInfo): string {
  const hasDist = hasDistBuild(project.rootDir);
  if (hasDist) {
    return path.join(project.rootDir, "dist", "lib", "bootstrap.js");
  }
  return project.entryFile;
}
```

**After**:
```typescript
export function resolveEntryFile(project: ProjectInfo): string {
  return project.entryFile;
}
```

### BUG-008 (P0): CJS Bundle Re-entry Causes Duplicate Bootstrap

**File**: `src/lib/bootstrap.ts`

**Problem**: `dist/index.cjs` (the framework's CJS bundle) included the complete code from `bootstrap.js`, including the module-level `isDirectRun` auto-execution logic. When the CLI forked a child process to run `bootstrap.js` (ESM), the following chain occurred:

1. `bootstrap.js` (ESM) module-level code detects `VEXT_MODE=start` → calls `detectAndStart()` → `bootstrap()`
2. Inside `bootstrap()`, step ② loads user plugins via `plugin-loader`
3. User plugin compiled as CJS calls `require("vextjs")` → loads `dist/index.cjs`
4. `index.cjs` module-level code also detects `VEXT_MODE=start` → triggers a **second** `detectAndStart()` → `bootstrap()`
5. Two bootstrap instances run in parallel within the same process

**Symptoms**:
- `[vextjs] initializing...` logged twice
- `[schema-dsl] i18n key 冲突` warnings (duplicate i18n registration)
- Plugins, services, routes loaded twice
- `EADDRINUSE: address already in use 0.0.0.0:3000` (second bootstrap tries to bind same port)

**Fix**: Added a `globalThis.__vext_bootstrap_started` re-entry guard before the `isDirectRun` check:

```typescript
const alreadyStarted = (globalThis as Record<string, unknown>).__vext_bootstrap_started === true;

if (isDirectRun && !alreadyStarted) {
  (globalThis as Record<string, unknown>).__vext_bootstrap_started = true;
  // ... auto-execution logic
}
```

The first entry sets the flag; subsequent `require("vextjs")` calls from user CJS code see the flag and skip auto-execution.

### BUG-009 (P1): `detectAndStart()` Catch Scope Too Broad

**File**: `src/lib/bootstrap.ts`

**Problem**: The `try/catch` in `detectAndStart()` wrapped both `loadConfig()` (config pre-load) and `bootstrap()` / `startClusterMaster()` calls. When `bootstrap()` threw a runtime error (e.g., `EADDRINUSE`), it was caught and misinterpreted as "config load failure", triggering a fallback second `bootstrap()` call — causing duplicate initialization within the same process.

**Fix**: `try/catch` now only wraps the `loadConfig()` pre-load phase. A `clusterEnabled` boolean flag is extracted inside the try block, then `bootstrap()` or `startClusterMaster()` is called **outside** the try/catch. Runtime errors from `bootstrap()` propagate directly to the CLI-level `.catch()` handler.

**Before**:
```typescript
async function detectAndStart(rootDir: string): Promise<void> {
  try {
    const config = await loadConfig(join(srcDir, "config"));
    const clusterConfig = config.cluster;
    if (clusterConfig?.enabled === true) {
      await startClusterMaster(rootDir);
    } else {
      await bootstrap(rootDir);
    }
  } catch (err) {
    console.warn(`[vextjs] config pre-load failed...`);
    await bootstrap(rootDir);  // ← second bootstrap on ANY error
  }
}
```

**After**:
```typescript
async function detectAndStart(rootDir: string): Promise<void> {
  let clusterEnabled = false;

  try {
    const config = await loadConfig(join(srcDir, "config"));
    const clusterConfig = config.cluster;
    clusterEnabled = clusterConfig?.enabled === true;
  } catch (err) {
    console.warn(`[vextjs] config pre-load failed...`);
  }

  // Outside try/catch — runtime errors propagate directly
  if (clusterEnabled) {
    await startClusterMaster(rootDir);
  } else {
    await bootstrap(rootDir);
  }
}
```

### BUG-010 (P1): BuildCompiler Missing `dist/package.json`

**File**: `src/lib/build/build-compiler.ts`

**Problem**: `DevCompiler` writes `{"type":"commonjs"}` to `.vext/dev/package.json` to ensure esbuild's CJS output is parsed correctly by Node.js. `BuildCompiler` was missing this logic. When the user's root `package.json` declares `"type": "module"` (which `vext-test` does), the CJS `.js` files in `dist/` were parsed as ESM by Node.js, causing `module is not defined` errors.

**Fix**: After successful esbuild compilation, `BuildCompiler.build()` now writes `{"type":"commonjs"}\n` to `outDir/package.json`:

```typescript
fs.writeFileSync(
  path.join(outDir, "package.json"),
  '{"type":"commonjs"}\n',
);
```

This ensures Node.js treats all `.js` files in `dist/` as CommonJS, consistent with `DevCompiler`'s behavior.

## Investigation Notes

### Ruled Out: schema-dsl ESM/CJS Dual Instance Hypothesis

During debugging, we investigated whether `monsqlize` (CJS, `require('schema-dsl')`) and `vext` (ESM, `import from 'schema-dsl'`) loaded two separate instances of `schema-dsl`, which could explain the i18n key conflicts.

**Finding**: schema-dsl's `index.mjs` (ESM wrapper) internally does `import schemaDsl from './index.js'`, referencing the same CJS module. Node.js CJS cache ensures `dsl`, `config`, `validate` function references are identical (`===` is `true`). Both packages resolve to the same physical path.

**Conclusion**: schema-dsl has only one instance. The i18n key conflicts were caused by BUG-008 (bootstrap called twice, each call registering i18n locales via `schemaAdapter.configure({ i18n })`).
