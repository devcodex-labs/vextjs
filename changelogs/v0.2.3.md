# v0.2.3 - 2026-03-31

## Highlights

- **F-01**: `VextRequest.route` — 5 个 Adapter 均注入路由模板字符串（如 `/users/:id`），解决 Prometheus 高基数问题
- **F-02**: `VextLoggerConfig.mixin` — 可配置用户自定义 mixin 函数，注入 `trace_id` / `span_id` 等字段，实现日志与链路追踪关联
- **F-03**: `RequestContextStore.traceId` / `spanId` — ALS 内置 trace context 字段，logger 内置 mixin 自动读取并注入日志
- **F-04 + F-05**: `website/docs/examples/opentelemetry.md` 全面重写 — 后端无关通用集成模式 + Cluster 多进程 OTEL 初始化完整指南

## New Features

### F-01: `VextRequest.route` — 路由模板注入

**背景**：

可观测性场景（Prometheus、OpenTelemetry Metrics）要求按**路由模板**聚合指标，而非按实际请求路径。例如：

```
❌ 高基数（按实际路径）：/users/123、/users/456、/users/789 → 三条时间序列
✅ 低基数（按模板）：/users/:id → 一条时间序列
```

vext 框架此前未向 handler / 中间件暴露路由模板字符串，用户只能通过 `req.path` 获取实际路径，在 Prometheus 等系统中造成严重的**基数爆炸**问题。

**变更内容**：

`VextRequest` 接口新增 `route: string` 属性，由各 Adapter 在路由匹配完成后自动注入：

```typescript
// 路由注册: app.get('/users/:id', ...)
// 请求: GET /users/abc-123

req.path; // '/users/abc-123'（实际路径，高基数）
req.route; // '/users/:id'（路由模板，低基数）✅
```

**5 个 Adapter 注入策略**：

| Adapter | 注入位置                   | 注入逻辑                                                            |
| ------- | -------------------------- | ------------------------------------------------------------------- |
| Native  | `onRouteMatch` 回调        | `req.route = store.routePath`（在 `RouteStore` 中存储注册时的模板） |
| Hono    | `registerRoute` 内         | `req.route = path`（Hono 使用统一的路径模板格式）                   |
| Fastify | `registerRoute` 内         | `req.route = fastifyPath`（Fastify 原生路径格式，无需转换）         |
| Express | `registerRoute` 内         | `req.route = expressPath`                                           |
| Koa     | `registerKoaMiddleware` 内 | `req.route = matched.entry.pattern`                                 |

**404 场景处理**：未匹配路由时 `req.route` 为空字符串 `''`，与 `req.path` 明确区分。

**新增 / 修改文件**：

| 文件                              | 操作 | 说明                                                           |
| --------------------------------- | ---- | -------------------------------------------------------------- |
| `src/types/request.ts`            | 修改 | `VextRequest` 接口新增 `route: string` 字段 + JSDoc            |
| `src/adapters/native/adapter.ts`  | 修改 | `RouteStore` 新增 `routePath`；`onRouteMatch` 注入 `req.route` |
| `src/adapters/native/request.ts`  | 修改 | `createVextRequest` 新增 `route: ''` 默认值                    |
| `src/adapters/hono/adapter.ts`    | 修改 | `registerRoute` 内注入 `req.route`                             |
| `src/adapters/hono/request.ts`    | 修改 | `createVextRequest` 新增 `route: ''` 默认值                    |
| `src/adapters/fastify/adapter.ts` | 修改 | `registerRoute` 内注入 `req.route`                             |

### F-02: `VextLoggerConfig.mixin` — 可配置日志 mixin

**背景**：

框架 logger（pino）的 mixin 逻辑此前硬编码，用户无法通过配置注入 `trace_id` / `span_id` 等字段，导致日志系统与链路追踪系统无法通过标准字段相互跳转。

**变更内容**：

`VextLoggerConfig` 接口新增可选 `mixin?: () => Record<string, unknown>` 字段。用户在 `vext.config.ts` 中配置后，其返回值在每条日志写入前与框架内置 mixin（`requestId` 注入）合并输出，**用户字段优先**。

```typescript
// src/config/production.ts
import { trace } from "@opentelemetry/api";

export default {
  logger: {
    mixin() {
      const span = trace.getActiveSpan();
      if (!span?.isRecording()) return {};
      const ctx = span.spanContext();
      return {
        trace_id: ctx.traceId,
        span_id: ctx.spanId,
      };
    },
  },
};
```

**合并规则**：

```typescript
// 伪代码（createLogger 内部逻辑）
const builtIn = { requestId: store?.requestId }; // 框架内置字段
const userFields = config.mixin?.() ?? {}; // 用户 mixin（可选）
return { ...builtIn, ...userFields }; // 用户字段优先
```

**零侵入保证**：未配置 `mixin` 时，代码路径与此前完全相同，零 overhead。

**新增 / 修改文件**：

| 文件                | 操作 | 说明                                                                    |
| ------------------- | ---- | ----------------------------------------------------------------------- |
| `src/types/app.ts`  | 修改 | `VextLoggerConfig` 新增 `mixin?: () => Record<string, unknown>` + JSDoc |
| `src/lib/logger.ts` | 修改 | `createLogger` pino mixin 合并用户 mixin 与内置字段                     |

### F-03: `RequestContextStore` trace context 字段

**背景**：

trace context（`traceId` / `spanId`）无法在 AsyncLocalStorage 中自动流转，需要用户在每条日志调用时手动传递，体验较差。

**变更内容**：

`RequestContextStore` 接口新增可选字段 `traceId?: string` 和 `spanId?: string`。用户的 tracing 中间件在请求开始时写入这两个字段，`logger.ts` 内置 mixin 在读取 `requestId` 的同时自动读取并注入日志：

```typescript
// 用户 tracing 中间件（示例）
app.use(async (req, res, next) => {
  const store = requestContext.getStore();
  if (store) {
    store.traceId = getCurrentTraceId(); // 写入 ALS
    store.spanId = getCurrentSpanId();
  }
  await next();
});

// 之后每条日志自动包含：
// { requestId: "...", trace_id: "abc123", span_id: "def456", message: "..." }
```

**与 F-02 的关系**：两者互补而非互斥。F-03 提供"无需配置"的零侵入体验（在 ALS 中写入即可），F-02 提供直接从 OTEL Context API 实时读取活跃 Span 的灵活扩展能力。

**日志字段名遵循 OTEL 语义约定**（下划线格式）：`trace_id`、`span_id`。

**新增 / 修改文件**：

| 文件                         | 操作 | 说明                                                                               |
| ---------------------------- | ---- | ---------------------------------------------------------------------------------- |
| `src/lib/request-context.ts` | 修改 | `RequestContextStore` 新增 `traceId?: string` · `spanId?: string` + JSDoc          |
| `src/lib/logger.ts`          | 修改 | 内置 mixin 读取 ALS `traceId` / `spanId`，存在时注入 `trace_id` / `span_id` 到日志 |

### F-04 + F-05: OpenTelemetry 集成文档全面重写

**背景**：

原文档（`website/docs/examples/opentelemetry.md`）存在以下问题：

1. `req.route?.path` 引用错误（F-01 完成前字段不存在）
2. `app.config.logger.mixin()` 调用写法类型不正确（F-02 完成前字段未在接口中声明）
3. 过度绑定特定后端（Jaeger / Grafana / Prometheus），不符合 OTEL 标准协议精神
4. Cluster 模式下 OTEL SDK 初始化方式未说明

**变更内容**（F-04 文档修复 + 通用化改造）：

- 修复 `req.route?.path` → `req.route`（F-01 实现后字段为 `string` 类型，直接使用）
- 修复 `app.config.logger.mixin()` → 正确配置写法（F-02 实现后字段已在接口中声明）
- 补全 tracing 中间件中写入 `requestContext` 的代码（配合 F-03）
- 导出器配置统一改为 `OTLPTraceExporter` + `OTLPMetricExporter`（OTLP 是 OTEL 标准协议，支持所有主流后端）
- 后端地址全部改为通过 **OTEL 标准环境变量** 配置（`OTEL_EXPORTER_OTLP_ENDPOINT`），不再硬编码 Jaeger / Prometheus URL
- 新增"支持的后端"对照表，说明通过更换 OTEL Collector exporter 配置即可对接任意后端

**变更内容**（F-05 Cluster 模式文档）：

- 新增 `## Cluster 模式` 章节（`website/docs/examples/opentelemetry.md` L807）
- 通过 `cluster.execArgv` 向 Worker 进程注入 `--import` 参数，实现每个 Worker 自动加载 `instrumentation.js`
- 明确说明 OTEL SDK 必须在**每个 Worker 进程**中独立初始化，Master 进程无需初始化

**修改文件**：

| 文件                                     | 操作 | 说明                                                       |
| ---------------------------------------- | ---- | ---------------------------------------------------------- |
| `website/docs/examples/opentelemetry.md` | 修改 | 修复 3 处类型错误引用 + 后端无关化改造 + 新增 Cluster 章节 |

## Implementation Notes

### 零外部依赖（Zero New Dependencies）

F-01 / F-02 / F-03 的所有框架层改动**不引入任何新的 npm 依赖**。`@opentelemetry/*` 系列包由用户按需安装，框架通过纯回调接口与 OTEL SDK 解耦。

### 向后兼容（Fully Backward Compatible）

| 场景                                    | v0.2.x 行为 | v0.2.3 行为                                                                      | Breaking？ |
| --------------------------------------- | ----------- | -------------------------------------------------------------------------------- | :--------: |
| 不使用 OTEL 的现有用户                  | —           | 零感知（`route` 字段存在但无需关注；`mixin` 未配置时行为不变；ALS 新字段为可选） |     ❌     |
| 已有 `VextRequest` 扩展类型声明         | —           | `route` 字段新增，TypeScript 不冲突（纯新增接口成员）                            |     ❌     |
| 已有 `RequestContextStore` 扩展类型声明 | —           | `traceId` / `spanId` 为可选字段，不影响已有声明                                  |     ❌     |

### 性能影响

| 功能                  |            未使用时 overhead             |                          使用时 overhead                          |
| --------------------- | :--------------------------------------: | :---------------------------------------------------------------: |
| `req.route` 注入      |      无（路由匹配后一次赋值，O(1)）      |                               同左                                |

## Migration Guide

### 无破坏性变更（Breaking Changes: None）

v0.2.3 对现有用户完全透明，无需修改任何配置或代码。

### 接入 OpenTelemetry 可观测性

如需接入 OTEL，参考 [OpenTelemetry 接入示例](/examples/opentelemetry) 的完整指南：

**最小接入（3 步）**：

```typescript
// 步骤 1：安装 OTEL SDK（用户项目，框架不引入依赖）
// npm install @opentelemetry/sdk-node @opentelemetry/auto-instrumentations-node @opentelemetry/exporter-trace-otlp-http

// 步骤 2：在 vext.config.ts 中配置 logger.mixin（可选，用于日志关联）
import { trace } from "@opentelemetry/api";
export default {
  logger: {
    mixin() {
      const span = trace.getActiveSpan();
      if (!span?.isRecording()) return {};
      const { traceId, spanId } = span.spanContext();
      return { trace_id: traceId, span_id: spanId };
    },
  },
};

// 步骤 3：在 Prometheus / OTEL Metrics 中使用 req.route 作为低基数标签
app.use(async (req, res, next) => {
  await next();
  metrics.httpRequestsTotal.inc({
    route: req.route,
    method: req.method,
    status: res.statusCode,
  });
});
```

**通过 OTEL 标准环境变量对接后端**（无需修改代码）：

```bash
# 对接 Jaeger（自托管）
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 node dist/index.js

# 对接 Datadog
OTEL_EXPORTER_OTLP_ENDPOINT=https://trace.agent.datadoghq.com DD_API_KEY=xxx node dist/index.js

# 对接阿里云 ARMS
OTEL_EXPORTER_OTLP_ENDPOINT=https://arms-trace-xxx.aliyuncs.com node dist/index.js
```

### Cluster 模式下接入 OTEL

在 `vext.config.ts` 中通过 `cluster.execArgv` 向每个 Worker 进程注入 OTEL SDK 加载参数：

```typescript
export default {
  cluster: {
    workers: 4,
    execArgv: ["--import", "./dist/instrumentation.js"],
  },
};
```

每个 Worker 独立初始化 OTEL SDK，Master 进程无需初始化。详见文档。
