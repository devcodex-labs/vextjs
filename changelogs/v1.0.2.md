# vextjs v1.0.2

**Date**: 2026-08-17
**Type**: Patch (backward-compatible runtime, documentation, dependency, and release-quality updates)

## Summary

`1.0.2` consolidates the backward-compatible work completed after `1.0.1`: route contracts are compiled once and used consistently by every supported adapter and generated contract surface; cluster/HMR recovery paths are hardened; and user-facing documentation now describes operational behavior and adapter benchmarking more precisely.

This is a patch release. Existing Vext applications do not need migration changes.

## Highlights

- **Consistent route response contracts**: JSON response schemas declared through `RouteOptions.responses` are compiled at registration time and shared by all five adapters, OpenAPI generation, route manifests, and generated client types. Documentation-only response schemas retain their existing serialization behavior.
- **Improved typed validation**: handlers can infer `req.valid(location)` from inline `validate` schemas through `schema-dsl@3.0.4`; explicit generics remain available for dynamic schemas.
- **More reliable development and production recovery**: cluster readiness timeout cleanup and HMR failure recovery are hardened so a failed replacement does not leave a stale worker or partially switched handler state.
- **Database integration update**: the direct `monsqlize` dependency is pinned to `3.3.0`; Vext retains the stable `app.db` facade while exposing the complete typed upstream instance through `app.monsqlize` and validating advanced constructor options.
- **Clearer operational documentation**: OpenAPI authentication and request semantics, upload temporary-file lifecycle, and configuration behavior are documented more explicitly in both locales.
- **Transparent benchmark guidance**: the public site presents the Adapter Matrix as a fixed Vext application with one adapter varied at a time. It explains why this is an adapter comparison rather than a cross-framework production ranking, and links reproducible data and method details for users who need to evaluate their own deployment configuration.
- **Release and CI hardening**: documentation/version synchronization, package composition, rendered documentation checks, coverage reporting, and current GitHub Actions runtime compatibility are validated in the release path.

## Non-goals

- No breaking public API, configuration, or adapter contract changes.
- No claim that one framework's published RPS universally predicts a different application's production throughput. Adapter Matrix results remain scoped to its documented fixed fixture.

## Upgrade

```bash
npm install vextjs@1.0.2
```

No source migration is required. If your application pins a Vext version in its quick-start or deployment examples, update that pin to `^1.0.2` when you are ready to consume the patch.

## Verification

- Full release preflight: formatting, linting, type checks, build, unit/integration/E2E tests, coverage, package composition, adapter and CLI contracts, documentation contracts, rendered site validation, and isolated packed-install validation.
- Independent `vextjs-test` consumer validation installs the candidate npm tarball rather than linking source, runs its build, and exercises the packaged runtime over HTTP.
- GitHub tag workflow independently re-runs version synchronization, CI, documentation build, final preflight, provenance npm publish, and GitHub Release creation.
