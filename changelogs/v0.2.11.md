## Changes Summary

Built-in multipart/form-data parsing with zero external dependencies.

VextJS now supports file uploads natively. Enable with `config.multipart.enabled: true` — the body-parser will automatically parse `multipart/form-data` requests using the Node.js 18+ `Request.formData()` Web API and fill `req.files`. No third-party library required.

---

## New Features

### Built-in Multipart / file upload parsing (`multipart.enabled`)

**Overview**:

A new `enabled` field is added to `VextMultipartConfig`. When set to `true`, the body-parser middleware detects `multipart/form-data` requests and parses them automatically, populating `req.files: ParsedFile[]`.

**Usage**:

```typescript
// vext.config.ts
export default defineConfig({
  multipart: {
    enabled: true,
    maxFileSize: 10 * 1024 * 1024, // 10MB (default)
    maxFiles: 10,                  // default
    allowedMimeTypes: ['image/jpeg', 'image/png'], // optional whitelist
  },
});
```

```typescript
// src/routes/upload.ts
app.post('/upload', {
  multipart: { files: { avatar: '用户头像' } },
}, async (req, res) => {
  const file = req.files?.find(f => f.fieldname === 'avatar');
  if (!file) return res.json({ code: 400, message: 'No file uploaded' }, 400);
  // file.buffer is the complete binary content, guaranteed lossless
  res.json({ filename: file.filename, size: file.size });
});
```

**Technical details**:

- **Zero dependencies**: Uses Node.js 18+ native `Request.formData()` Web API (project already requires `engines: >=18.0.0`)
- **Unified buffer parse path**: All adapters (including Hono) go through `_getRawBodyBuffer()` → `new Request(url, { body: rawBuffer, headers })` → `.formData()`. This guarantees the raw buffer cache is always populated before formData parsing, enabling downstream code (plugins, middleware) to call `_getRawBodyBuffer()` safely after body-parser runs.
- **Validation**: `maxFiles` (413), `maxFileSize` (413), `allowedMimeTypes` (415) are enforced before populating `req.files`
- **Default off**: `enabled` defaults to `false`; when not enabled, multipart requests are skipped with zero performance impact

## Binary channel infrastructure (T1–T16, shipped in 0.2.11)

The following foundational changes were also included in this release (implemented prior to the built-in parsing feature):

### `req._getRawBodyBuffer()` — typed binary accessor on all adapters

`VextRequest` now officially exposes `_getRawBodyBuffer(): Promise<Buffer>` in the TypeScript interface. All 5 adapters implement it:

- **Hono**: `Buffer.from(await c.req.arrayBuffer())` — Buffer-first cache, string derived lazily
- **Express / Koa / Fastify**: returns existing pre-collected Buffer reference (zero copy)
- **Native**: `IncomingMessage` stream read once into Buffer; string derived lazily

Previously, plugins used `(req as any)._getRawBodyBuffer()`. This is now unnecessary — the method is on the public interface with full type inference.

### `req.files` — typed file list on `VextRequest`

```typescript
interface VextRequest {
  files?: ParsedFile[] // populated by body-parser when multipart.enabled = true
}
```

### `ParsedFile` interface

```typescript
interface ParsedFile {
  fieldname: string
  filename: string
  mimetype: string
  buffer: Buffer
  size: number
}
```

### `VextMultipartConfig` / `MultipartRouteConfig` types (`src/types/app.ts`)

- `VextConfig.multipart?: VextMultipartConfig` — global multipart configuration
- `RouteOptions.multipart?: MultipartRouteConfig` — per-route file field declaration (used by OpenAPI generator)

### Route-level multipart override (`MultipartRouteConfig.enabled`)

In addition to global `config.multipart.enabled`, individual routes can enable and configure multipart parsing independently:

```typescript
app.post('/upload', {
  multipart: {
    enabled: true,             // enable per-route (even if global is off)
    maxFileSize: 1024,         // override global maxFileSize
    maxFiles: 1,               // limit file count
    allowedMimeTypes: ['image/png', 'image/jpeg'],
    files: { file: 'Image file' },
  },
}, handler);
```

`createRouteMultipartMiddleware()` is injected by `router-loader` (step 2.7) when `route.options.multipart.enabled === true`. When the global body-parser has already parsed the request (`req.files !== undefined`), the route middleware performs a second-pass validation only (enforcing per-route limits), without re-parsing the stream.

### OpenAPI `multipart/form-data` requestBody generation

When a route declares `multipart: { files: { avatar: '...' } }`, the OpenAPI generator now emits:

```yaml
requestBody:
  required: true
  content:
    multipart/form-data:
      schema:
        type: object
        properties:
          avatar:
            type: string
            format: binary
```

### Fastify `bodyLimit` auto-linking

`bodyLimit` now defaults to `Math.max(multipart.maxFileSize, 1MB)` when `multipart.maxFileSize` is configured, preventing Fastify from rejecting large file uploads with 413 before they reach the vext middleware chain.

## Breaking Changes

None. All changes are additive and backward-compatible:

- `files` field is optional (`?`) on `VextRequest`
- `multipart.enabled` defaults to `false` — existing applications are unaffected
- `_getRawBodyBuffer()` was previously an untyped internal method; adding it to the interface is a non-breaking type improvement

## Bug Fixes

### `parseMultipart`: Hono stream consumption issue

**Problem**: The original implementation had a Hono-specific fast path that called `c.req.raw.formData()` directly. The Web API `Request.formData()` consumes the underlying `ReadableStream`, making it impossible for subsequent calls to `c.req.arrayBuffer()` (used by `_getRawBodyBuffer()`) to read the body. As a result, `_rawBufferCache` was never populated — any plugin or middleware reading `_getRawBodyBuffer()` after body-parser returned an empty Buffer.

**Fix**: Removed the Hono-specific path. All adapters now use the unified buffer path: `_getRawBodyBuffer()` fills the cache first, then `new Request(url, { body: rawBuffer })` is used for `formData()` parsing. The raw buffer cache is guaranteed to be populated before multipart parsing begins.

**File**: `src/lib/middlewares/body-parser.ts`

### `ParsedFile` exported from public API

`ParsedFile` was previously defined in `src/types/request.ts` but not re-exported from the package entry point. As a result `import type { ParsedFile } from 'vextjs'` failed with a compile error when used in plugins.

**Fix**: Added `ParsedFile` to `src/types/index.ts` re-exports and `src/index.ts` type export block.

**Files**: `src/types/index.ts`, `src/index.ts`

### `website/docs/guide/plugins.md` — custom parsing section corrected

The "Advanced: Custom parsing" section incorrectly stated that `multipart.enabled` should be kept `false` when using a busboy plugin. In practice the plugin already includes a guard (`if (req.files !== undefined) { await next(); return; }`) that safely skips re-parsing when the global body-parser has already run, making both coexistence and exclusive modes work correctly.

**Fix**: Replaced the "keep `false`" recommendation with a description of both supported modes (exclusive and coexistence), and added the guard code to the example.

**File**: `website/docs/guide/plugins.md`
